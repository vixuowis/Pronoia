seq="auto">一、核心算法改进（按收益预期排序）</h2><h3>1. 引入「单事件多 Horizon 联合预测 Head」，替代当前单点分类</h3><ul><li><b>问题：</b>当前模型对每个事件仅输出一个方向（up/down/neutral）+ 一个置信度，与评价的 T+1/3/5/7/15/30/60 + avg_all 多 Horizon 目标不对齐。Case 中大量负例呈现 <b>T+3 与 T+60 方向翻转</b>（如 B01、B02、B04、B08、B10），模型被迫在「短期 vs 长期」取平均，导致 neutral 占比过高（60.3%）与 AUC 偏低。</li><li><b>方案：</b>在输出层拆为 3 个并行头：    <ul><li>Short Head：T+1 / T+3 / T+5 联合；</li><li>Mid Head：T+7 / T+15；</li><li>Long Head：T+30 / T+60 / avg_all。</li></ul></li><li><b>预期收益：</b>直接修复「短期反转长期」类错误。预计 Strict ACC ↑ 5~8pp，neutral 占比 ↓ 10~15pp，avg_all AUC ↑ 0.03~0.05。</li></ul><h3>2. 证据链重打分：从「启发式加权」升级为「可学习 Cross-Attention Mixer」</h3><ul><li><b>问题：</b>当前决策链由 event_study_skill（T0 AR / pre20 drift / sell_the_news）、公告分类器（info_tier / merger prior）、结构化分析净分、基本面历史以<b>手工规则加权 + 净分阈值判断</b>组合。G03/G05 的高置信正确与 B03/B09 的反向大错，都源于「sell_the_news 系数 / CN 并购先验偏空」被僵化套用——B03 中要约收购与普通重组完全不同，但先验一致压低 up 信号。</li><li><b>方案：</b>引入 <b>Evidence Mixer</b>（3~4 层轻量 Transformer Cross-Attention），将每条证据（T0 AR、pre5/pre20 drift、sell_the_news 系数、info_tier 分类、event_type 先验 embedding、consensus_net、基本面 vector、结构化净分）编码为独立 token，与事件文本 CLS 向量做 cross-attention，输出最终方向 logits。    <ol><li seq="1">证据 token 自带类型 embedding + 数值标准化（z-score / rank-gauss）；</li><li>加入 Gating：在「公告文本 info_tier=low（如 B05/B06/B08/B09 程序性说明）」时自动下调文本先验权重、上调行情信号权重；在真正有指引数值的事件（如 G01/G07）上调文本 / 基本面权重；</li><li>增加 Market-Attention 头：CN / US 使用独立 Mixture-of-Experts，避免 US 宏观事件被 CN 并购先验反向污染。</li></ol></li><li><b>预期收益：</b>系统性解决「文本弱信号绑架决策」和「市场/类型特异性先验被平均」两类根因。预计分市场 AUC 偏差（CN-US）从当前约 0.05 缩小到 0.02 以内，Strict ACC ↑ 4~6pp。</li></ul><h3>3. 置信度校准：Platt Scaling + 方向-幅度二元校准，替代「LLM 自报置信」</h3><ul><li><b>问题：</b>当前 conf 为 LLM 自报数值，在 0.5~0.8 区间几乎线性分布，但实际 ECE 差。B02（conf=0.70 全周期错）与 B04（conf=0.72 错）说明「高置信 ≠ 高正确」；Spearman(conf, |CAR|)=0.287，置信度与真实波动弱相关。</li><li><b>方案：</b><ol><li seq="1">在 Evidence Mixer 输出上新增一个二分类 Calibration Head（<b>High-Conf Correct vs Low-Conf / Incorrect</b>），训练目标由 (pred, GT, |CAR|) 联合计算标签（strict correct ∧ |CAR|≥1% → positive，否则 negative）；</li><li>推理时，将原始 LLM conf 与 Calibration Head 做 Platt Scaling 融合：<code>final_conf = σ(a·logit + b·LLM_conf + c)</code>，参数 a/b/c 用验证集最大 LogLikelihood 拟合；</li><li>引入 Confidence-Preserving Abstention：当 final_conf &lt; 阈值时自动 neutral，阈值按 F1-macro 验证集自适应。</li></ol></li><li><b>预期收益：</b>ECE ↓ 50%+，conf 与正确率的 ROC-AUC ↑ 0.10+。运营档 conf≥0.65 的 T+3 Strict ACC 从当前 70.4% 提升到 75~78%。</li></ul><h3>4. 方向判别中的「时序动量 / 反转」可学习 Kernel</h3><ul><li><b>问题：</b>B 类错误高频出现「T+3 与 T+30/T+60 反向」，模型对「短期反转长期」vs「持续趋势」缺乏时序建模能力。当前仅使用 pre5 / pre20 两个标量，完全丢弃 pre[-30, -1] 的分布形状与极值信息。</li><li><b>方案：</b>将 pre[-60, 0] 相对收益序列（对齐基准后 61 维）过一个 3 层 1D-CNN + 1 层 LSTM 小网络，输出 Momentum Embedding，拼接进 Evidence Mixer。额外加辅助分类任务：预测该事件未来 60 天属于「持续 / 反转 / 震荡」三类中的哪一类，监督信号从真实 CAR 曲线聚类得到。</li><li><b>预期收益：</b>B01 / B02 / B04 / B08 / B10 这类「短期错 / 长期对」或「T+1 同向但长期反转」case 的纠正率约 40~50%。T+60 Strict ACC 单独 ↑ 6~9pp。</li></ul><h3>5. 事件类型误标 Detection（Out-of-Distribution Head）</h3><ul><li><b>问题：</b>Case B05 中，标签「公司指引上调/下调」实际对应重组程序性说明公告，event_type_l2 本身被上游误标，导致模型按「指引」逻辑触发「文本无数值 → down」，而真实 GT 是重组预期引发的大下跌（pred=neutral 仍算 strict wrong）。据观察，这类误标在数据集里约 5~10%。</li><li><b>方案：</b>用事件文本训练一个独立的 Multi-label Event Classifier（6 类 + OTHER，输出 Shannon Entropy）。推理时当 entropy ≥ threshold，显式注入「类型不确定度」进 Evidence Mixer，并降低对应 event_type 先验权重。</li><li><b>预期收益：</b>缓解 B05 / B06 这类证据链断裂的系统性误判。neutral 漏捕捉 case 预计下降 20~30%。</li></ul><h2 seq="auto">二、系统架构改进</h2><h3>6. 异步推理 + 多 Skill 并行化，降低单事件端到端延迟</h3><ul><li><b>问题：</b>当前 team_full runner 4 并发跑完 1000 条耗时数小时，单事件 6~8 秒。event_study_skill、基本面查询、公告分类三者串行，LLM 推理与结构化分数计算未并行。</li><li><b>方案：</b><ol><li seq="1">将「行情信号 / 公告分类 / 基本面查询 / 结构化净分 / 共识分数」拆为 <b>独立 Skill Node</b>，用 DAG 调度器在单事件内三路并行（行情 + 公告 + 基本面），最后在 Evidence Mixer 节点汇合；</li><li>增加 <b>Batch Runner V2</b>：在 team_full 之外引入 Batch mode（每批 32~128 条做 LLM batching），KV cache 共享 + Flash Attention。Skill 级调用走 batching：event_study_skill 一次批量取 64 个事件的 AR/drift，减少 roundtrip × 64；</li><li>引入 Checkpoint-level Recovery：当前 trajectory ckpt 仅存结果，不存中间 Skill 输出。改为 DAG 节点级持久化（Redis / LevelDB），中断恢复直接跳过已完成 Skill，预计中断恢复时间 ↓ 90%。</li></ol></li><li><b>系统收益：</b>单事件 P50 延迟 ↓ 50~70%，1000 条在同 4 并发下时间缩到 30~60min。</li></ul><h3>7. 可插拔 Horizon-Specific Routing 网关（避免「单模型包打天下」）</h3><ul><li><b>问题：</b>当前单一 team 模型同时服务 T+1 交易信号到 T+60 配置型判断，是 AUC 与 neutral 占比差的架构根因。短期（T+1/3）主要靠行情/事件冲击，长期（T+30/60）主要靠基本面和趋势，两套信号分布差异大。</li><li><b>方案：</b>在 Evidence Mixer 上层引入 <b>Horizon Router</b>：    <ul><li>Short Route：T+1 / T+3 → 重行情、drift、T0 AR；文本仅做分类，不深入数值理解；</li><li>Mid Route：T+7 / T+15 → 均衡；</li><li>Long Route：T+30 / T+60 → 重基本面、行业 beta、consensus、事件类型长期效应先验。</li></ul></li><li><b>预期收益：</b>不同调用方（日内交易 / 组合调仓 / 主题配置）各取所需。预计 Short Route（T+3）Strict ACC ↑ 7pp，Long Route（avg_all）AUC ↑ 0.04。</li></ul><h3>8. 流式评分 + Shadow 双轨部署，支持真 Online 指标监控</h3><ul><li><b>问题：</b>当前 metrics 靠回测批量计算（bt score），上线后无法逐日追踪 AUC / 分市场 ACC。离线指标与在线质量可能严重脱节，上游事件文本或行情数据源 schema 变更（如 B01 symbol 串扰）只能等下一轮回测发现。</li><li><b>方案：</b><ol><li seq="1"><b>Prediction Warehouse：</b>每次生产推理写 Kafka → OLAP（Doris / ClickHouse），主键 (event_id, run_id, horizon)，分区 event_date；</li><li><b>Label ETL：</b>每日 UTC+0 09:00 自动增量计算各事件最新 T+N CAR（T+30 需要 30 天后最终值，支持 repeated UPSERT + version）。已成熟 label 写入状态 horizon_matured；</li><li><b>Shadow 双轨：</b>新模型版本上线时 Shadow Mode 跑 100% 流量但不对外，对比主模型 AUC / ACC / Calibration，连续 7 天 ≥ 主模型（含分市场、分事件类型 z-test）才允许切主；</li><li><b>Data Drift Detector：</b>监控 event_type_l2 分布、symbol-公告匹配度、info_tier 分布、T0 AR 分布、pre20 drift 分布 5 类特征的 PSI，PSI ≥ 0.25 触发飞书告警，强制锁止高置信路由。</li></ol></li><li><b>系统收益：</b>把「跑回测→算指标→出报告」从一次性人工动作变为每日自动化，下一次质量事故的发现时间从「两周」缩短到「1 天内」。</li></ul><h3>9. Team Runner 引入多团队辩论 + 裁决器（MoA / Debate）</h3><ul><li><b>问题：</b>当前 team_full 是单 team 通过，但 B02 / B04 等高置信错误显示，单一 LLM 的结构化判断存在锚定偏差——一条 T0 AR 被过度放大后，后续证据全部向其对齐。</li><li><b>方案：</b>升级 team_runner → <b>DebateRunnerV2</b>：    <ul><li>Team A（Bear）：只看 down 侧证据（sell_the_news、利空基本面、负 drift、AR down），输出 down 置信；</li><li>Team B（Bull）：只看 up 侧证据（要约溢价、超跌反弹、利率下降、AR up），输出 up 置信；</li><li>Team C（Market Neutral）：只看 info_tier、|AR| 幅度、consensus_entropy，输出 neutral 置信；</li><li>Adjudicator：接收三个 Team 的结构化输出（含各自 rationale），用一个较小 LLM 或 Evidence Mixer 的 Cross-Attention 1 天。预期 neutral 占比 ↓ 8~12pp，Strict ACC ↑ 3~5pp。</li></ul><h3>L1-4 Prompt 模板注入「错误模式 RAG」+ 「同类历史 Case 3 条」，做 Harness 层 in-context 自纠正</h3><ul><li><b>问题：</b>当前每个事件的 Prompt 都只含「任务定义 + token| = 0） ∧ （"consensus/prev/last" 全部为空）</code>，就把文本证据全部 bypass，强制只用行情 + drift + 事件类型先验（先验 weight 再减半），防止 B06 这种「证据链全断却走了中立流程」。</li></ol></li><li><b>自进化方式：</b>每次回测 strict wrong 样本都跑一次 Guard 规则命中率统计，如果某条规则没命中但实际是数据质量问题，就加进规则集合（GitHub PR + code review，<b>不改模型</b>）。</li><li><b>落地成本：</b>≈ 1 天。预期 B01 / B05 / B06 / B07 / B08 这类脏数据问题至少一半被前置修复。</li></ul><h3>L1-6 Confidence 重校准（Platt Scaling，Harness 层后处理，不训模型）</h3><ul><li><b>问题：</b>B01 (conf 0.74)、B04 (conf 0.72) 高置信错，说明 LLM 自报 conf 有「自信膨胀」。Spearman(conf, |CAR|) 只有 0.287，置信度与真实波动关联弱。</li><li><b>方案：</b>在 Harness 层做 Platt Scaling 的<b>离线拟合 + 在线查表</b>：    <ol><li seq="1">用当前 1000 条回测结果，分 6 个分桶（pred=up/down × conf 三档），对每桶拟合 strict_correct_rate 作为校准后 conf；</li><li>再加一个 <code>|T0 AR| + |pre20|</code> 维度的二维分桶（3×3），做二维校准表 <code>calibration_table.json</code>；</li><li>推理时在 Harness 输出之前，用查表值替换掉 LLM 原始 conf。</li></ol></li><li><b>自进化方式：</b>每次 bt score 跑完重新生成 calibration_table.json（纯离线统计，0.5 秒跑完）。</li><li><b>落地成本：</b>≈ 3 小时。预期高置信错误率（conf≥0.70）直接下降 25%。</li></ul><h3>L1-7 Horizon-Specific 多 Prompt 模板（复用同一模型，不改交互）</h3><ul><li><b>问题：</b>B01 / B02 / B04 / B08 / B10 都是「短期对 / 长期翻转」或者「短期错 / 长期对」，当前模型只输出一个方向，被迫对齐 avg_all。但 API 实际下游用户用的 horizon 差异大，同一个 pred 对所有人都不够友好。</li><li><b>方案：</b>在 Harness 层把同一个事件按 <b>Short（T+3）、Mid（T+15）、Long（avg_all）</b> 分别走三套独立的 Prompt 模板：    <ul><li><b>Short 模板</b>：system prompt 明确强调「T0 AR、pre5/pre20 drift 权重 = 70%，文本权重 = 20%，基本面权重 = 10%」；</li><li><b>Mid 模板：</b>均衡 40/35/25；</li><li><b>Long 模板：</b>强调基本面、行业 beta、consensus_net，文本/行情 15/35/50。</li></ul></li><li><b>自进化方式：</b>每个 template 单独跑 bt score 出 metrics_short / metrics_mid / metrics_long，哪个口径掉分就针对性调 template 里的权重说明 prompt。</li><li><b>落地成本：</b>≈ 1~2 天。T+3 Strict ACC 预计 ↑ 4~6pp，T+30/60 Strict ACC ↑ 5~7pp，API 兼容性 100%。</li></ul><h3>L1 汇总：7 项，全部可自进化，零训练，3~5 天可全量上线</h3><callout emoji="🚀"><p><b>上线顺序推荐：</b>L1-5（脏数据 Guard）0 风险先上 → L1-2（STN 门控）+ L1-6（Conf 校准表）24h 内上完 → L1-1（先验分桶表）+ L1-3（阈值路由表）2 天内上完 → L1-4（错误模式 RAG）+ L1-7（三模板路由）3~5 天内上完。</p><p><b>L1 层总预期收益：</b>沿用当前 1000 条回测评估口径：Strict ACC ↑ 10~14pp（从 31.4% → 41~45%），avg_all AUC ↑ 0.05~0.07（从 0.477 → 0.53~0.55），neutral 占比 ↓ 15~20pp（从 60.3% → 40~45%），运营档 conf≥0.65 ACC 从 70.4% → 76~79%。</p></callout><hr/><h2 seq="auto">L2 · 动模型：RLVR / 专项训练 / 自进化层</h2><p>L1 拿到确定收益、且三个路由模板的错误分布稳定后，再切入 L2。所有 L2 项目都<b>假设 L1 已经在线上跑</b>（脏数据先滤掉、先验/阈值已经最优、错误模式已 in-context），避免在脏基座上浪费训练预算。</p><h3>L2-1 RLVR 训练：用「真实 pred→GT 收益 + 校准惩罚」作奖励函数</h3><ul><li><b>为什么要 RLVR：</b>L1 的 Prompt 规则再精细也是离散的，无法学到「在证据冲突微妙时如何加权」这种连续决策。</li><li><b>设置：</b>沿用当前证据链输入（行情/公告文本/基本面/drift/STN/consensus）不变，RLVR 的 Agent 只学两件事：  <ol><li seq="1">evidence weighting：给 8 条证据各学一个 0~1 权重（Market×EventType 条件下）；</li><li>threshold 选择：在「neutral 窗口收窄 / 放宽」之间做连续决策（可训练的 beta 分布采样）。</li></ol></li><li><b>Reward 函数（关键）：</b><br/><code>R = 1.0 × strict_correct − 0.3 × strict_wrong − 0.1× neutral_penalty×(1−|CAR_avg|/5%) + 0.4 × spearman(conf, |CAR|) − 0.5 × ECE</code><br/>用加权 Strict ACC 为主，同时惩罚：当 |CAR| 大时还 neutral、conf 与真实幅度不校准、ECE 过高等 3 件事（刚好对应 L1 之后的剩余残差）。</li><li><b>预计收益：</b>在 L1 基础上再 + Strict ACC 4~6pp，AUC +0.03~0.05，ECE 再降 40%。</li></ul><h3>L2-2 Evidence Mixer + Horizon 多头的 SFT 小模型（冻结基座，只训 adapter）</h3><ul><li>在 L1-7 三模板验证了「Short/Mid/Long 三路由有效」之后，把三模板的「权重配比说明 prompt」直接学进 <b>1 个 small adapter / LoRA</b>：输出 7 个 horizon 的方向 head + 1 个 conf head。基座主模型完全冻结，训练成本可控（单卡 2~3 天可完成）。</li><li>为什么放在 L2：需要先有 L1-7 稳定输出的伪标签（pred_short/mid/long 三个方向）做监督信号，否则一上来训 head 容易学到错误归因。</li></ul><h3>L2-3 DebateRunnerV2 + 裁决器的 PPO 自博弈进化</h3><ul><li>基于 L1-4 的 mistake_memory + 常见错误模式构造 Bull/Bear/Neutral 三辩模板（L1 级 prompt 层就可以先做，证明有效后再训裁决器）。裁决器在 L2 用 PPO 训练：奖励 = 三辩输出的最终裁决 strict_correct_rate − 裁决延迟成本。</li><li>优点：自博弈可不断吃 L1 新产生的 mistake_memory，每轮回测都能产出一批新的辩论样本，真正实现「越跑越强」的自进化闭环。</li></ul><h3>L2-4 Online RLVR（Shadow Mode 实时学习）：流式指标 + 在线小步更新</h3><ul><li>只有在 L1 的 <b>Prediction Warehouse</b>（可先不做 Kafka，直接用 MySQL upsert + 每日 ETL 计算最新 T+N CAR，纯 Harness 存储层就行，不需要流式基建）成熟后再开启：每天把 matured 的 label 回流，对 L2-1 的 RLVR agent 做一次 online 小步 update（KL penalty ≤ 0.001，防止灾难性遗忘）。</li><li><b>注意：</b>这一步完全不要求流式架构，<b>每日批处理即可</b>。把「流式」这个词换成「每日离线增量回灌」就可以 0 基建改造启动。核心是 Shadow Mode + 在线学习，不是 Kafka。</li></ul><h2 seq="auto">两层路线图 &amp;
